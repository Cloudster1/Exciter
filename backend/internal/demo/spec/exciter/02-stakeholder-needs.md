# Stakeholder needs

What the people who work with Exciter need from it.

### SN-1 Know what a change touches
type: Stakeholder need
priority: must

A requirements engineer needs to see which requirements depend on one that changed, so that they are reviewed again.

### SN-2 Show that every requirement is tested
type: Stakeholder need
priority: must

A test manager needs to see which requirements a passing test case verifies and which no test case verifies yet.

### SN-3 Write the specification where it is read
type: Stakeholder need
priority: must

A requirements engineer needs to write, order and read requirements as one numbered specification, with the types and fields their project uses, and to find an earlier wording again.

### SN-4 Decide who may see and change what
type: Stakeholder need
priority: must

A project administrator needs to say which people and groups may view, comment on, edit, approve and administer a project, so that nobody changes or approves what they should not.

### SN-5 Review and approve with proof
type: Stakeholder need
priority: must

A reviewer needs to decide on a requirement as it stands in one revision, and a quality manager needs the decision kept with who made it and what they saw, so that an audit finds it.

### SN-6 Freeze what was agreed
type: Stakeholder need
priority: must

A project lead needs to keep the specification as it was agreed at a release, to compare it with the present one, and to know that a signed release never changes.

### SN-7 Find requirements quickly
type: Stakeholder need
priority: should

A person who reads a large specification needs to find requirements by their words, their fields and their links, and to keep a search they use often.

### SN-8 Exchange requirements with other tools
type: Stakeholder need
priority: should

A requirements engineer needs to bring requirements in from spreadsheets, Word documents and other tools, and to hand a specification to customers and suppliers in the formats they use.

### SN-9 Work with the issues and pages of the suite
type: Stakeholder need
priority: must

A developer and a technical writer need to see a requirement beside the issues that implement it and the pages that explain it, and to see the requirement where they work.

### SN-10 Plan, run and record tests
type: Stakeholder need
priority: must

A tester needs to write test cases with steps, plan a test round against a version, record each result and raise an issue from a failure, and a pipeline needs to report its results.

### SN-11 Write clear, consistent requirements
type: Stakeholder need
priority: should

An author needs help to write requirements that are unambiguous, use the project's terms, say each thing once and are reused where they repeat.

### SN-12 See the state of the project
type: Stakeholder need
priority: should

A project lead needs charts and counts over the requirements of a project, and values computed from the requirements' own fields, without a spreadsheet kept by hand.

### SN-13 Manage risks beside the requirements
type: Stakeholder need
priority: could

A safety engineer needs to rate risks before and after mitigation, to see which mitigations are in effect, and to trace them like requirements.

### SN-14 Automate and let assistants help
type: Stakeholder need
priority: should

An integrator needs a documented interface, tokens that do less than their owner may, and events pushed to other systems, and a person needs an assistant to work with requirements as that person and no more.

### SN-15 Run one installation safely
type: Stakeholder need
priority: must

An administrator needs people to sign in once through the suite's identity provider, to run Exciter beside the other tools, and to rely on it keeping its data private, bounded and recoverable.
